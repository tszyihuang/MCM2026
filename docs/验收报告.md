# 验收报告（模拟器自检 + 策略演练）

本报告记录自建模拟器的验收过程、结果与已知限制。
全部数据由 `tools/smoke_test.py`、`tools/spec_audit.py`、`tests/` 测试套件与
`tools/run_batch.py` 直接产生。

---

## 1. 验收环境

| 项目 | 值 |
| --- | --- |
| 运行环境 | Python 3.9+；模拟器、部署程序与测试套件只用标准库，求解器进程内评测另需 numpy |
| 模拟器接口 | `http://127.0.0.1:2026`（默认） |
| 界面 | `http://127.0.0.1:2027`（默认） |
| 测试窗口 / 程序运行 / 虚拟活动上限 | 1500 s / 1200 s（20 分钟）/ 360000 s（100 小时，仅防止死循环） |
| 干扰源个数 | 10~16（每局随机） |

> 计时口径：**现实程序运行时间**上限为 20 分钟（`max_real_duration_s = 1200`），
> **虚拟世界活动时长**上限为 100 小时（`max_virtual_duration_s = 360000`，附件1 2.5 说明
> 其通常不构成约束，仅为防止程序死循环）。两者相互独立，任一到达都会结束测试。

### 2.4 模拟器正确性交叉验证

* **物理量对照**：以案例真值为参照，逐点校验 `/measure` 的 `direction`/`near`/`no_signal`
  与 `/clear` 的 `success`/`no_target_in_range`，边界值（5 m、20 m、有效半径、覆盖角 ±90°）
  均按「含边界」实现并通过断言。
* **时间守恒**：每局测试满足
  `移动 + 频道切换 + 检测 + 清除 = 虚拟总时间 = 动作日志累计耗时`（误差 < 1e-3 s）。
* **上界对照**：`tools/oracle.py` 给出「忽略检测耗时、且每次动作都能看到全部频道」的
  理想贪心上界。注意它的"预算"是**虚拟时间**，与题目约束的**现实**程序运行时间口径不同，
  不能用来论证「不可能清除全部」。

## 3. 正式测试取数

正式测试由 `python tools/run_batch.py --problem 3 --module formal --runs 3` 连续执行
（`--runs` 不得超过模块的 3 次机会上限），模拟器每次随机生成案例；案例编码与

## 5. 计时口径勘误（已修复的历史缺陷）

题目有两个**相互独立**的上限：虚拟世界活动 100 小时、现实程序运行 20 分钟。
二者不可混用，原因见 `README.md` 文首的 WARNING 框。

曾出现过的 A 级缺陷：把**虚拟**上限当成**现实**预算
（`min(现实剩余时间, virtual_limit_s - 已用虚拟时间)`，且 `virtual_limit_s` 硬编码 1195.0），
导致程序只消耗约 0.4 s 现实时间（占 1200 s 预算的 0.03%）就自行收尾，清除率被压到约 14%。

修复方式：

* 预算判断**只以 `/enter` 返回的 `remaining_real_duration_s` 为准**；
* 虚拟上限改为官方 `MAX_VIRTUAL_S = 360000`（纯兜底安全网，正常不触发）；
* 删除由虚拟上限反推动作数的逻辑；
* 测试套件分别断言两个口径：`program_runtime_s <= 1225`（现实）与
  `total_duration_s <= 360000`（虚拟），不再把虚拟总时长与现实的 1200 s 相比。

## 6. 已知限制

1. 模拟器与策略均为**自研复现**，全部数字来自本地模拟器，不代表官方模拟器的最终成绩。
2. 问题3 的残余漏源（约 0.18%）集中在边缘与低检测概率区域；问题4 通过贴边补扫环把
   标定集、独立测试集与 2000 局全新种子全部补齐到 100%，但该结论仍受自建模拟器的案例分布约束。
3. `tools/oracle.py` 给出的上界是**虚拟时间口径**的理想贪心，不能直接与正式测试成绩比较。
